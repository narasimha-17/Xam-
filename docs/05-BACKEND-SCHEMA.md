# Document 05 — Backend Schema (Data Model & Auth Architecture)

All tables use an integer auto-increment primary key (`id`), not UUIDs. All timestamps are `timestamptz` with a `server_default=now()`. Managed via SQLAlchemy 2.0 declarative models + one Alembic migration (autogenerated from the models, applied with `alembic upgrade head`).

## Table: match_pairs
Used by `match` questions. Each row **is** the correct pairing (left ↔ right) — there's no separate "correct answer" field; grading checks whether the student's submitted right-side choice for a given pair id equals that same pair id.
| Column | Type | Notes |
|---|---|---|
| id | int, PK | |
| question_id | int, FK → questions.id, CASCADE | |
| left_text | text | |
| right_text | text | |
| order | int | |

The student-facing serialization splits each pair into a `match_left` item and a `match_right` item (both keyed by the same pair `id`), and **shuffles the display order of the right-hand column** per request so the correct pairing isn't visually obvious from list order.

## Table: attempt_answers
| Column | Type | Notes |
|---|---|---|
| id | int, PK | |
| attempt_id | int, FK → exam_attempts.id, CASCADE | |
| question_id | int, FK → questions.id, CASCADE | |
| answer_json | JSON | shape depends on question type (see below) |
| is_correct | bool, nullable | null is used for match/fill-blank/coding partial-credit cases where "correct" isn't strictly binary |
| points_awarded | float | default 0.0 |
| graded_detail | JSON, nullable | the full `correct_answer` detail computed at submit time (see grading service) — persisted so the results page never has to recompute it. For non-coding types this is cheap to recompute anyway (pure DB lookup); for coding it's the actual JDoodle execution output per test case, which would otherwise cost another JDoodle API call (and quota) every time the student revisits their results |

**`answer_json` shapes** (also what the client POSTs on submit):
- mcq: `{"selected_option_id": <int>}`
- maq: `{"selected_option_ids": [<int>, ...]}`
- match: `{"pairs": {"<left_pair_id>": <right_pair_id>, ...}}`
- fill_blank: `{"blanks": {"<blank_index>": "<text>"}}`
- coding: `{"language": "python"|"java"|"cpp", "code": "<submitted source>"}`

**Coding `graded_detail` shape**: `{"test_case_results": [{"input", "expected_output", "actual_output", "is_sample", "passed", "error"}, ...], "passed_count": <int>, "total_count": <int>}` — points awarded are `question.points * passed_count / total_count`.

## Relationships Summary
```
users 1──* subjects (created_by)
subjects 1──* topics
subjects 1──* pdfs, 1──* exams, 1──* discussion_threads
exams 1──* questions
questions 1──* question_options / match_pairs / fill_blank_answers / test_cases

```

## Auth Model
Custom JWT (not a hosted auth provider). `POST /auth/login` (OAuth2 password-flow form) and `/auth/register` both return `{access_token, token_type, user}`. The token payload is `{sub: user_id, role, exp}`. `get_current_user` decodes the bearer token and loads the user; `require_role(*roles)` / `require_admin` gate admin-only endpoints. There is no row-level security at the database layer — all authorization is enforced in the FastAPI dependency layer.

## User Roles & Permissions
- **student** (default on self-registration): read subjects/PDFs/published exams, take exams, read/write discussion posts (own posts only for delete), read own progress.
- **admin** (seeded via `python -m app.seed_admin`, not self-assignable): everything a student can do, plus create/edit subjects & topics, upload/delete PDFs, create/publish/delete exams, delete any discussion thread/post.

## File Storage
Local filesystem under `backend/uploads/pdfs/`, gitignored. Filenames are randomly generated (`{uuid4().hex}.pdf`) to avoid collisions and path traversal; the original title is stored in the `pdfs.title` column and re-attached as the `Content-Disposition` filename (sanitized) on download. Max upload size enforced at 25MB, content-type must be `application/pdf`.

## Sensitive Fields
Only `hashed_password` — bcrypt-hashed, never returned in any API response (the `UserOut` schema excludes it entirely). No payment or other sensitive fields exist in this version.
